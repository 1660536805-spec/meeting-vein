## 2. 产品到底要实现什么

### 2.1 一句话定义

会脉是**实时、共享、可人工修正的会议结构化记忆**：把发言整理为议题、观点、论据、结论和待办，保留彼此的支持、反对、重复与取代关系，并允许随时追溯到原话。

### 2.2 核心承诺与边界

| 维度 | 产品承诺 |
| --- | --- |
| 会前 | 用议程或会议标题建立讨论骨架；进入会议时知道本次要解决什么。 |
| 会中 | 语音或手动输入进入分析链，新增信息归到正确议题；已说过的内容可复用；分歧与结论演变可见。 |
| 人工控制 | 人能修正、锁定、撤销 AI 的整理结果，修改不会被下一轮推理静默覆盖。 |
| 会后 | 可从结论或待办回看依据、原话与版本，并交付可读的纪要或快照。 |
| 职责边界 | AI 维护看板，不抢发言权、不出声主持、不替会议平台提供音视频通话。 |

最有辨识度的能力应当是：**一条新发言如何改变已有讨论结构，而且改变有来源、可解释、可撤销。** 图谱和看板娘服务于这个过程，不能替代这个过程的清晰呈现。

### 2.3 主要用户任务

1. 主持人或参会人在 10 秒内知道现在讨论哪一题、已有何种共识、还有什么未定。
2. 记录员能确认某个 AI 结论所依据的原话，必要时修正分类或关联。
3. 会后负责人能拿走少量明确的行动项，知道负责人、期限和来源。

## 3. 当前能力与产品缺口

| 链路 | 当前融合版已有的基础 | 当前缺口或需确认之处 |
| --- | --- | --- |
| 输入 | 手动发言、录音/上传、本机 ASR、流式临时文字与分段事件；ASR 不可用时手动输入仍可用。 | 真实麦克风到图谱的端到端表现仍需单独验收；流式分段提交失败的恢复路径不完整。 |
| 分析 | 双 Agent、Mock/可配置真实 LLM、会议专家提示词、同会议串行处理、失败批次补偿。 | 演示数据的分类和归组需人工标注评估；“事件已入库”和“已完成落图”目前容易混成一个成功状态。 |
| 看板 | X6 图谱、焦点深链、关系筛选、节点移动/连线调整/删除、PNG/SVG 导出。 | 大图首次打开难读；焦点附近关系线过密；编辑能力不足以兑现“人工可控”的完整承诺。 |
| 结构与追溯 | 同一份 cells 渲染议题结构；Store B 记录原话并用 `metadata_refs` 反查；历史会议与版本快照。 | 结构视图把所有有向边当父子边；从摘要或议题到原话的路径不够直接；快照链接依赖同一服务的数据文件。 |
| 反馈 | 右侧焦点/未决/下一步、看板娘状态、ASR 与 LLM 模式状态。 | “当前焦点”是最后两个相关类型节点，并非按重要性或当前议题选出；“未决 0”只数 conflict 节点，与反对关系可能不一致；已加载会议仍显示“等待讨论”。 |

## 4. 产品层面的主要判断

### 4.1 先解决“看懂”，再增加图谱能力

200 句的示例图能证明系统处理了大量内容，但默认画面里根节点被左侧原话栏覆盖，连线密集，75% 缩放下节点文字偏小。首次打开没有清晰回答“这场会议得出了什么”。用户必须自己探索全图，Demo 的价值传递速度因此变慢。

**目标体验**：首屏先看到简短的会议结论卡；点一条观点进入局部图谱；再点节点看原话与证据；最后能修正或导出。图谱仍是核心资产，但承担“解释结构”的任务，而非承担首屏所有信息。

### 4.2 把“结构树”和“语义关系网”分开

`issues-view.ts` 和 `board/render.ts` 当前都把图中的全部边用于推导父子层级；而边同时含 `subordinate/support/oppose/duplicate/replace`。这些关系不总是树的父子关系。随着跨观点的反驳、重复或取代增加，可能出现多父、错误归类、循环或布局跳变。应建立**稳定的结构归属**（每节点一个主父级）和**可多条的语义关系**（支持、反对、重复、取代）两套明确契约，再由两个视图共享同一投影结果。

### 4.3 “可信”比“智能感”更重要

Demo 的助手在已加载讨论时显示“等待讨论”，原话列表的发言人带 `user_` 前缀且时间均为 `00:00`。这些不是单纯视觉瑕疵：它们削弱观众对实时性、说话人识别和证据链的信任。MockLLM 与真实 LLM 的模式、识别完成与落图完成的状态，也必须清楚区分。

## 5. 建议的目标体验

```mermaid
flowchart LR
  A[会前：标题/议程/参与者] --> B[会中：语音或文本输入]
  B --> C[转写与原话入库]
  C --> D[观点/证据/行动提取]
  D --> E[结构归属与语义关系]
  E --> F[可读概览]
  F --> G[局部关系图]
  G --> H[原话与变更依据]
  H --> I[人工确认/修正]
  I --> J[纪要/快照/行动清单]
```

工作台建议采用三层信息密度：

- **概览层**：议题、2–4 条关键观点、明确结论、未决事项、前三项行动；让第一次打开的人迅速理解会议。
- **探索层**：以当前议题或焦点为中心的局部关系图；节点及其父级、子级、直接证据完整可见，其他内容灰化，重点节点保持不透明的深色底。
- **证据层**：点节点出现来源抽屉，显示原话、说话人、时间、AI 判断理由与相关版本；支持纠错。

P0 面向下一轮演示；P1 面向可用 MVP；P2 面向扩展。工作量用 S/M/L 表示相对规模，需拆票后由团队估算。每项都应从样例会议和空白新会议两条路径验收。

### P0：让 Demo 可信、可讲、可恢复

| ID | 优化项 / 建议做法 | 验收标准 | 规模 |
| --- | --- | --- | --- |
| P0-01 | **默认概览**：加载已有会议时先展示辩题、双方立场、核心分歧、明确结论和前三项行动；提供“展开关系图”。空白会议展示输入引导。概览从现有 cells/元数据派生，不复制一份独立真相。 | 不操作页面也能在 10 秒内说出会议主题、两种主要观点和下一步；空白会议不会显示伪结论。 | M |

| P0-03 | **关系筛选反馈**：显示匹配边数，说明筛选仅改变显示范围；零匹配时给出“当前焦点没有反驳关系”，允许一键清除筛选。 | “反驳”筛选无结果时不留下看似断开的孤立节点；筛选和焦点叠加的规则可理解。 | S |
| P0-04 | **演示数据清理**：统一示例会议名称、发言数口径、发言人显示名与时间；把“已分析的历史会议”与“正在讨论”状态分开；去掉无信息量的“要点”标题。 | 加载示例会议不再显示“等待讨论”；原话有可解释的时间/顺序；没有 `user_` 技术前缀。 | S |
| P0-05 | **输入处理回执**：前端分别显示“已接收原话 / 等待分析 / 已更新看板 / 更新失败可重试”。流式分段保存失败时保留同一事件 ID 与文本，允许重发；不因已切出分段就丢弃整段兜底。 | 人为制造看板提交失败时不会显示“已送达看板”，且用户能重试，最终不会重复建点。 | M |
| P0-06 | **Demo 模式标识**：清楚显示当前为示例数据、Mock 分析或已配置的真实模型；模式状态应由实际运行的客户端报告。 | 观众不会把规则 Mock 输出误认为真实模型分析；状态与后端实例一致。 | S |

**代码依据**：`decision-panel.ts` 的焦点取 `slice(-2)`，未决只数未解决 `conflict` 节点；`panel.ts` 的 `liveSegments` 在提交成功前递增，失败分段未进 `pendingEvent`；`server.py` 的 `_store_utterance` 即使编排失败也可返回已入库成功；`main.ts` 的关系透镜只控制边可见性。这些结论是静态代码检查与页面观察，实施前仍需针对当前分支复核。

| ID | 优化项 / 建议做法 | 验收标准 | 规模 |

## 7. 数据与工程优化原则

1. **状态机贯穿输入到落图。** 建议为每条发言记录 `received → transcribed → queued → analyzed → committed / failed`，前后端用相同事件 ID；“已接收”不等于“已更新看板”。失败批次补偿应在 UI 中可见。
2. **一份结构真相。** Store A 保留节点和关系，Store B 保留原话；结构父级与语义边分别校验。节点至少有类型、标题、来源引用、创建者、确认状态与版本；行动项另有负责人、期限、完成状态。先定义迁移策略，再重做布局。
3. **把来源和不确定性带到界面。** AI 输出节点时保存 evidence ID 与置信/判定依据。没有来源的摘要可以出现，但应标“待核对”；人工确认后再作为正式结论导出。
4. **把真实性和可用性分开度量。** ASR 临时字幕的响应时间、最终转写准确率、要点上板延迟、分类/归属质量是不同指标。不要用“文字出现很快”替代“结论正确”。
5. **大图按需呈现。** 当前 `board.update` 广播完整 cells，前端重新渲染整图；先测量更新耗时、画布节点数与交互卡顿，再决定是否上增量协议。首要优化仍是默认信息层级。
6. **隐私边界清楚。** 默认本机处理音频与存储会议数据；配置外部 LLM 时，界面应说明文本会发送到该服务。分享 token 作为读取凭据处理，提供过期或撤销策略后再做公网分享。
7. **素材授权作为发布门槛。** 仓库 README 标明当前 Live2D 素材为 CC BY-NC-SA 4.0；商业化前需取得相应授权或更换素材。

## 9. 指标与验收口径

需求大纲给出的初版目标包括：要点上板 P95 ≤10 秒、重要要点召回率 ≥80%、归属准确率 ≥85%、重复识别准确率 ≥75%、相悖结论召回率 ≥70%、人工编辑保留率 100%、看板复用率 ≥60%。**这些是待内测校准的目标，不是当前测量结果。**

建议另补四组产品指标：

- **理解速度**：首次进入后能否说出主题、双方观点、未决与下一步；记录完成所需时间。
- **可追溯率**：被展示为结论/行动的节点中，有效原话引用的比例。
- **修正成本**：用户纠正节点类型、父级或文本所需点击数与时间；修正后一轮自动更新的保留率。
- **可靠性**：发言接收成功率、落图成功率、失败重试恢复率、同一事件重复落图率，以及 200/500/1000 节点下的更新和交互耗时。

## 10. 暂不扩大范围的事项

先不要把语音主持、自动打断、发言排名或会议平台替代能力纳入当前路线；这些与已确认的产品边界不一致。投票、跨会议知识图谱和复杂看板动画可以保留为后续探索，前提是单场会议的**可读、可信、可修正、可交付**已经成立。

## 11. 市场对比与差异化定位（2026-10-06 补充）

### 11.1 比较口径

本节只比较各产品公开页面明确描述的能力与会脉当前仓库能力，未购买或完整试用竞品；功能可能因版本、套餐和地区不同而变化。**竞品官网没有提到某项能力，不等于它一定没有。**“会脉当前”依据本地融合工作树的代码与 Demo；“潜在优势”须经真实会议评测后才可转为对外宣称。

### 11.2 代表性产品与用户得到的价值

| 类型与代表 | 官方公开能力 | 对会脉的启示 |
| --- | --- | --- |
| 会议平台内置 AI：[腾讯会议 AI 小助手](https://meeting.tencent.com/support/topic/2082/)、[Zoom AI Companion](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0057748)、[Teams Copilot](https://learn.microsoft.com/en-us/training/modules/copilot-meeting-productivity/) | 会议内容问答、摘要、关键点与后续行动直接嵌在既有会议平台中。腾讯会议在开启实时转写后可针对会议内容提问；Zoom 提供会中追问和创建任务/文档入口。 | 会脉目前没有它们的平台入口、账号、分享与跨设备触达能力；不宜以“也能生成纪要”正面竞争。 |

### 11.3 会脉真正可以建立的区别

1. **从“会议发生了什么”走向“决定为何改变”。** 当前数据模型已经有 `support / oppose / duplicate / replace` 等关系、节点来源引用与版本历史。若能稳定识别“新证据反驳旧观点”“新结论取代旧结论”，用户得到的是决策过程，而不只是摘要。与 TalkGraph 等可视化产品比较时，重点应落在这些**关系语义和变更证据**，不能只展示一张图。
2. **会中形成共享的论证空间。** 用户定位一个议题后，应直接看见主张、支持证据、反证、未决和当前结论，并能当场修正。这样适合方案评审、需求评审、辩论、风险评估等分歧明显的会议。当前 Demo 有节点、语义透镜与结构视图基础，但默认画面和筛选反馈尚不足以支持这个承诺。
3. **人工判断可进入结构真相。** 后端已有字段编辑保护、锁定和版本机制的基础；产品目标是人改过的文本、类型、归属和重要性在后续 AI 更新中保留。完整编辑界面与可理解的变更记录尚需补齐。
4. **可选择本机音频处理。** 融合版用本地 ASR 和本机存储，适合希望控制音频流向的场景。但如果启用外部 LLM，转写文本可能发送到配置的服务；因此只能说“本机 ASR / 可配置模型边界”，不能笼统声称“会议内容全程不出本机”。MeetGraph 等也提供本地转写选项，本机处理不是唯一卖点。

### 11.4 已有能力、潜力与短板必须分开

| 比较维度 | 会脉当前 Demo | 与市场相比的判断 |
| --- | --- | --- |

| 结构化纪要与行动项 | 有节点和右侧“下一步”，但行动项缺负责人/期限的稳定字段，首屏概览不够成熟。 | 目前弱于成熟纪要工具的会后交付。 |

### 11.5 推荐的市场定位与一句话表达

**目标细分场景**：需要比较方案、处理分歧、保留决策依据的团队会议。此类会议的痛点不是“缺一份纪要”，而是“忘记为何选择 A、为何否定 B，之后又重复争论”。这是基于当前产品设计和竞品公开功能作出的定位推断，仍需用户访谈验证。

建议对外表达：

> **会脉把会议中的观点、证据、反驳和决议变化整理成可追溯、可修正的实时看板，让团队看清结论是怎样形成的。**

对外材料可用“讨论脉络 / 决策依据 / 人工可控”作为三个关键词。避免使用“首个会议图谱”“唯一无机器人”“行业最准确转写”等缺乏证据且与已有产品能力冲突的表述。

### 11.6 下一轮 Demo 应证明的五件事

1. 一条新发言进入后，图上**已有观点被更新或补充**，而非机械地新增一张卡。
2. 一个反方论据明确连接到被反驳的主张；筛选“反驳”能显示原因和来源。
3. 当新结论推翻旧结论，两者都保留，并标明“取代”与对应原话。
4. 人工修正一次错误归类，下一轮 AI 更新后仍保持修正。
5. 从最终结论回看原话、说话人、时间及版本；无法确认的内容明确标记待核对。

如果这五项能在真实输入与 200 句会议样本中稳定演示，会脉的价值就能与常规“转写 → 摘要 → 待办”路径清楚区分；若做不到，应先把它们列为产品验证任务，暂不把概念优势写成已验证的效果。
