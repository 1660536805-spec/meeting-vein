## 0. 产品定位（已确认）

**本产品是「AI 会议秘书」，不是「AI 主持人」。**

三条已确认的边界：

1. **发言权归人。** 主持人（人）持有发言权，AI 不参与发言、不抢话、不出声、不打断。
2. **AI 只做一件事**：维护会议看板结构图。
3. **更新看板结构图的触发源只有两个**：
   - **① 实时会议状态**（自动）—— 从会议语音与讨论进展推导
   - **② 用户指令**（手动）—— 用户显式要求的结构调整

---

## 0.1 核心概念：看板结构图

看板不是一列要点清单，而是一张**持续演进的结构图** —— 用节点和边表达议题、要点、结论之间的从属与支撑关系。

**节点类型**

| 类型 | 说明 | 示例 |
|---|---|---|
| 议题 Issue | 顶层分支，通常来自议程 | 「Q3 增长策略」 |
| 要点 Point | 讨论中产生的论点、事实、约束 | 「渠道成本比去年涨 30%」 |
| 结论 Conclusion | 达成的决定 | 「Q3 主攻存量复购」 |
| 待办 Action | 需跟进事项 | 「张三本周出渠道成本明细」 |
| 分歧 Disagreement | 尚未收敛的对立观点 | 「是否砍掉低毛利渠道」 |
| 问题 Question | 提出但未解答 | 「投放 ROI 怎么算？」 |

**边类型**

| 关系 | 含义 |
|---|---|
| 从属 | 子议题 / 支撑要点挂在父节点下 |
| 支撑 / 反对 | 要点之间的论证关系 |
| 重复 | 同一要点的多次提及 |
| **取代** | 新结论替代旧结论 |

> **「取代」边是关键设计。** 面对「相悖结论」痛点，不做静默覆盖，也不做阻断拦截，而是**保留演进痕迹**：新旧结论都留在图上，用「取代」边连接，谁、何时、基于什么推翻的，一目了然。

## 1. 项目背景与目标

### 1.1 背景与痛点

大多数组织的会议冗长低效。但问题的根源往往不是「没人主持」，而是**讨论过程缺少一份实时、共享、结构化的记忆** —— 信息只存在于参会人的短期记忆和各自零散的笔记里。

由此产生四类典型问题：

| 痛点 | 具体表现 | 后果 |
|---|---|---|
| 冗长低效 | 议程推进慢，大量时间消耗在重复铺垫上 | 会议时长失控，产出与投入不成比例 |
| 主题跑偏 | 讨论脱离当前议题，且无人及时拉回 | 关键议题没有结论 |
| 重复讨论 | 前边讨论过的问题，后边又被提起，且常被当成新问题重新讨论一遍 | 时间二次浪费 |
| 信息流失 → 结论相悖 | 讨论细节遗忘大半，基于被遗忘的片段重新推导，得出与先前相悖的结论 | 决议不可靠，会后返工 |

这四类问题相互放大：**遗忘导致重复，重复导致跑偏，跑偏最终产出相悖结论。**

### 1.2 产品定位

一句话：**一个会议秘书 —— 把会议讨论实时沉淀为一张可编辑的结构化看板，让全场始终看得见「已经讨论过什么」「哪些最重要」「哪里出现了出入」。**

与「AI 主持人」的关键区别：

| 维度 | AI 主持人 | 本产品（会议秘书） |
|---|---|---|
| 职责 | 推进议程、控场、分配发言 | 记录、整理、呈现 |
| 发言权 | 持有（会出声） | **不持有，全程不出声** |
| 对会议的干预 | 打断、点名、提醒超时 | 不打断，只更新看板 |
| 核心产出 | 会议按计划推进 | **实时看板结构图** |

### 1.3 目标（Goals）

- **G1 实时沉淀**：讨论内容实时进入看板结构图，不依赖参会人记忆，也不依赖会后补记。
- **G2 要点上板**：从讨论中抽取要点，实时挂载到结构图的正确位置。
- **G3 重要性分级**：对节点做重要性评估，高重要性节点在图上被**放大 / 高亮**。
- **G4 重复提及识别**：已讨论过的要点再次被提起时，关联到既有节点而非新建。
- **G5 相悖结论可见**：新结论与既有结论冲突时，以「取代」或「分歧」关系呈现，不让矛盾被静默接受。
- **G6 人工可控**：看板可编辑，人工修改不被后续自动更新覆盖。

> G4 / G5 直接对应 1.1 中的「重复讨论」与「结论相悖」，是产品的差异化核心，也是技术上的主要难点。

### 1.4 非目标（Non-goals）

- **不做发言**：不出声、不播报、不打断（发言权归人）
- **不做发言权管理**：不排队、不点名、不做发言均衡
- **不做议程推进与控场**：不催时长、不判定跑题并干预
- 不替代会议平台本身（不做音视频编解码、不做会议 SDK）
- 不做参会人绩效评估或发言排名
- 不做法律级存证（不追求逐字稿的法律效力）

### 1.5 成功指标

| 指标 | 目标值 | 衡量方式 |
|---|---|---|
| 要点上板延迟 | P95 ≤ 10s | 从讨论发生到看板出现对应节点 |
| 要点召回率 | ≥ 80% | 人工标注的重要要点中，被自动捕获的比例 |
| 节点归属准确率 | ≥ 85% | 要点被挂到正确父节点/议题的比例 |
| 重复提及识别准确率 | ≥ 75% | 正确关联到既有节点的比例 |
| 相悖结论召回率 | ≥ 70% | 真实矛盾中被标记出来的比例（宁多勿漏，见 4.4） |
| 人工编辑保留率 | 100% | 人工修改在后续自动更新中不被覆盖 |
| 看板复用率 | ≥ 60% | 会后直接以看板整理成正式纪要的会议占比 |

> 均为初版目标值，需在内测中重新标定。

## 2. 目标用户与典型场景

### 2.1 用户角色

| 角色 | 诉求 |
|---|---|
| **会议主持人（人）** | 专心主持，不必分心记录；发言权牢牢在自己手里，不被 AI 抢话 |
| **会议记录员** | 从全程速记转为审阅与修正看板 |
| **参会人** | 随时看到讨论进展；说过的话被记住了，不必重复 |
| 会议组织者 | 会后直接拿看板生成纪要，不必等速记整理 |

### 2.2 典型场景

- **S1 需求评审 / 方案讨论**：最易跑题与重复，看板可作为「已讨论过」的公共证据。
- **S2 周会 / 站会**：15 人以内，重点是待办提取与跨周追踪。
- **S3 长会 / 多议题会议**：2 小时以上，信息流失最严重，看板作为外部记忆价值最大。

## 4. 关键机制

> 本章 4.1–4.4 为**设计建议**，尚未经确认；4.5 为约束条件。

### 4.1 双通道更新机制

看板结构图的更新只有两个来源，**指令通道优先级高于自动通道**。

**通道 A — 自动（实时会议状态）**

```
ASR 转写流
   └─ 句子级缓冲（等待语义完整）
        └─ 要点抽取 + 分类
             └─ 与既有节点比对（向量检索召回 → LLM 判定）
                  ├─ 高相似  → 判定为重复提及，累加提及次数，不新建
                  ├─ 部分相关 → 挂载为子节点或建立关系边
                  └─ 无关     → 新建节点
                       └─ 结构重排 + 重要性重算 → 看板增量更新
```

**通道 B — 指令（用户）**

- **自然语言指令**：「这条标为重点」「合并这两条」「新建一个议题」
- **直接编辑**：改文本、改类型、拖拽层级
- **显式锁定**：冻结节点，AI 只读

> 两条通道可能同时改同一块板，冲突处理见 4.4。

### 4.2 触发策略

不采用「每一句话都调用模型」的轮询方式，成本与噪声都不可接受。采用**事件触发**：

- 句子语义完整（ASR 断句 + 置信度达标）
- 检测到结论性/决策性表述（「那就这么定了」「我们统一一下」）
- 检测到待办表述（「张三你跟一下」）
- 一段连续发言结束（说话人切换）
- 静默超过阈值

### 4.3 重要性评估

候选信号与权重（**Q2 已定：以「产出结论/待办」与「被支撑/被反驳」为核心加权维度**）：

| 信号 | 权重倾向 | 理由 |
|---|---|---|
| 是否产出结论或待办 | ★★★ 最高自动权重 | 有产出说明讨论收敛、有结果，是看板最有价值的信息 |
| 被支撑次数（被其他要点/结论论证） | ★★ | 多人论证 → 共识度高 → 重要 |
| 被反驳次数（被其他要点/结论挑战） | ★★ | 被挑战 → 存在分歧或风险点，需持续可见 |
| 被提及次数 | ★ | 跨时间反复提及 = 强重要性信号（但权重低于「有产出」） |
| 参与讨论的人数 | ★ | 多人参与 > 单人独白 |
| 讨论持续时长 | ★ | 争议大或复杂度高的点 |
| 是否被标记为分歧 | ★★ | 未收敛的分歧需要持续可见 |
| 人工显式提升 | 最高优先级 | 覆盖全部自动评分 |

> **权重设计要点**：「是否产出结论/待办」与「被支撑/被反驳」权重高于单纯的「被提及次数」。原因——被反复提及却无结论的闲聊不应被放大；而**达成结论的要点、被多人支撑或挑战的要点**，才是真正需要全场聚焦的信息。人工显式提升永远覆盖自动评分（见 4.4）。

**输出**：重要性等级 → 映射为视觉权重（尺寸 / 字号 / 高亮 / 布局位置）。

> **硬约束：重要性必须可解释。** 用户要能看到「这条为什么被放大」（如「产出结论 + 被 3 人支撑」）。不可解释的自动放大比不放大更糟 —— 会直接摧毁信任。

### 4.4 人工编辑与自动更新的冲突处理（建议方案）

这是看板能否成立的关键问题：AI 在持续更新，用户也在改同一块板。

建议采用**字段级权限**而非节点级：

| 字段 | 归属 |
|---|---|
| 节点文本 | 人工编辑后即冻结，AI 不再改写 |
| 节点类型 | 人工可改，AI 可建议 |
| 位置 / 层级 | 人工拖拽后冻结，AI 不再自动重排 |
| 提及次数 | AI 独占，人工不可改 |
| 关系边 | 双写，冲突时保留双方并标记 |
| 重要性 | AI 打分 + 人工可覆盖（人工值优先） |

配套规则：
- 人工动过的节点打上「已人工修改」标记，AI 的后续改动记入版本历史而非直接覆盖
- 「锁定」是显式的更强一档，AI 完全只读
- 所有自动改动可回溯，支持一键回滚某次自动更新

### 4.5 时延预算

| 环节 | 预算 |
|---|---|
| ASR 流式出字 | ≤ 300ms |
| 要点抽取 + 挂载 + 上板 | ≤ 10s（P95） |
| 用户指令响应 | ≤ 2s |

> 不含 TTS，预算比 v0.2 宽松。但「上板延迟」直接影响用户是否相信看板是"实时"的，仍是核心约束。

## 5. 非功能需求

| 类别 | 需求 |
|---|---|
| 性能 | 要点上板 P95 ≤ 10s；指令响应 ≤ 2s；ASR 流式出字 ≤ 300ms |
| 并发 | 单场 ≥ 100 人；单实例 ≥ 20 场并发（首版） |
| 可用性 | 看板服务可用性 ≥ 99.5%；模型调用失败时**降级为停止自动更新**，看板保持可读可编辑，不阻塞会议 |
| 实时推送 | 看板变更通过实时通道推送，多人协同编辑需处理并发写 |
| 隐私 | **音频不存储**（Q8 已定）；仅存储转写文本与看板快照，支持随时删除 |
| 安全 | 会议内容加密传输与落盘；不做跨租户数据训练 |
| 成本 | 事件触发而非全量调用；单场成本需实测 |
| 可观测 | 记录每次自动更新的触发原因、上下文摘要、耗时，便于回溯调优 |
| 合规 | 会议开始时需明确告知参会人「AI 正在记录并生成看板」 |

## 6. 系统架构概览

### 6.1 模块划分

```
会议平台接入层（音频流）
        │
        └── ASR 服务（流式转写 + 说话人分离）
                │
                ▼
        ┌───────────────────────────────┐
        │  看板引擎 Board Engine         │
        │  ├─ 触发判定                    │
        │  ├─ 要点抽取 + 分类（LLM）      │
        │  ├─ 节点匹配 / 去重（检索+LLM） │
        │  ├─ 相悖结论检测（LLM）         │
        │  └─ 重要性评估                  │
        └───────┬───────────────────────┘
                │
                ▼
        ┌───────────────────────────────┐
        │  看板服务                       │
        │  ├─ 结构图存储（节点 / 边）     │
        │  ├─ 字段级权限与版本历史        │
        │  └─ 实时推送                    │
        └───────┬───────────────────────┘
                │
     ┌──────────┴──────────┐
     ▼                     ▼
 前端看板（结构图可视化）   用户指令解析（LLM）

会后：看板快照 → 纪要生成服务（批处理）→ 导出 / 同步
```

### 6.2 大模型接入接口模式

> 本设计**不锁定具体模型厂商与型号**，只约定 Agent 调用大模型的**统一接入接口模式**；模型可插拔、可配置、可替换。

- **统一接入接口（LLM Gateway）**：Agent 所有大模型调用走一套**通用接入接口**（OpenAI 兼容协议），由配置指定后端模型。要点抽取、节点匹配判定、相悖结论检测、指令解析、纪要生成等全部环节共用同一套接口封装，不因模型差异改动业务代码。
- **接口需具备的关键能力（作为接口契约，而非某厂商专属特性）**：
  - **结构化输出**：节点与边以稳定 JSON 返回（硬需求，禁止自由文本解析）。
  - **流式输出**：用于实时推送与长响应场景。
  - **前缀复用 / Prompt Caching**：议程、参会人、历史结构图等稳定前缀复用，降低计费与首字延迟；缓存前缀须字节稳定，不得插入时间戳或递增 ID。
  - **推理分档**：同一接口支持按档位切换轻量↔高质量——会中实时链路走低档保延迟，会后纪要生成走高档保质量，便于统一调优。
  - **思考可视化（可选）**：调试期可开启「为什么判定为重复 / 相悖」的推理摘要，便于回溯。
- **模型路由对业务透明**：具体后端用哪个模型、是否对轻量子链路路由更低延迟模型，仅由配置与实测决定（见 Q7），接口层对上层无感。

### 6.3 数据流

**会中**
```
音频流 → ASR → 触发判定 →（触发时）LLM 抽取/匹配/检测 → 结构图变更
      → 字段级权限校验 → 实时推送 → 前端看板
用户指令 → LLM 解析 → 结构图变更 →（同上）
```

**会后**
```
看板快照 + 转写全文 → 批处理生成纪要 → 人工校对 → 导出 / 同步
```

## 9. 风险与挑战

| 风险 | 影响 | 应对 |
|---|---|---|
| 要点抽取质量不足 | 看板充满噪声，用户放弃 | M1 优先验证；抽不准时宁可少上板 |
| **看板分散注意力** | 参会人盯着看板而非讨论，适得其反 | 控制更新频率与动效；提供「安静模式」；避免每次更新都弹动 |
| 重要性评估主观 | 放大的不是用户认为重要的 | 评估必须可解释 + 人工可覆盖（4.3 / 4.4） |
| 相悖结论误报 | 频繁假警报会摧毁信任 | 采用「呈现」而非「阻断」；标注置信度；宁多勿漏但不打断 |
| 不上板延迟不达标 | 用户不再相信看板是实时的 | 事件触发 + 增量更新；M1 实测 |
| 人工编辑被覆盖 | 用户不再愿意编辑 | 字段级权限 + 版本历史（4.4），编辑保留率要求 100% |
| 多人并发编辑冲突 | 协同编辑出现覆盖写 | 采用协同编辑协议；关键操作加锁 |
| 模型调用失败 | 看板停止更新 | 降级为停止自动更新，看板仍可读可编辑，不阻塞会议 |
| 长会议上下文膨胀 | 延迟与成本上升 | 结构化上下文（用结构图摘要替代全量转写）做增量；成本需实测 |

> **风险排除（2026-09-19 评审）**：「参会人隐私顾虑 / 不敢畅所欲言」**不再列为跟踪风险**——看板默认全员可见（Q6）且音频不存储（Q8），需要私密的发言场景由参会人自行闭麦管理，不额外设计隐私隔离机制。

| # | 问题 | 影响 |
|---|---|---|
| Q1 | 首发接入哪个会议平台？（**已定：腾讯会议**） | 决定接入层实现与可行性 |

| Q5 | **相悖结论如何呈现**（**已定：并列分歧 + 置信度提示，不静默取代**） | 影响 G5 |

## 11. 术语表

| 术语 | 含义 |
|---|---|
| ASR | Automatic Speech Recognition，语音识别 |
| 看板结构图 | 用节点与边表达的会议讨论结构，本产品的核心产出 |
| 节点 | 结构图中的一条信息单元（议题/要点/结论/待办/分歧/问题） |
| 边 | 节点之间的关系（从属/支撑/反对/重复/取代） |
| 提及次数 | 同一要点在会议中被重复提到的累计次数 |
| 取代 | 新结论替代旧结论的关系，保留演进痕迹而非静默覆盖 |
| 上板延迟 | 从讨论发生到看板出现对应节点的时间 |
| 锁定 | 用户显式冻结节点，AI 只读 |
