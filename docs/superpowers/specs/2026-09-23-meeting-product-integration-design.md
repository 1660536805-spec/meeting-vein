# AI 会议秘书与本地 ASR 融合设计

## 目标与基线

面向黑客松演示，交付一个用户从同一网页录音、查看转写、生成并操作会议结构图的本地产品。断开语音服务或缺少模型时，网页仍可用手动发言驱动看板，并清楚说明故障原因。真实音频与真实大模型能力分别验证，不能把模拟结果标称为真实识别或真实推理。

以 Gitee `wz50525/ai_meeting_organizer` 的 `dev` 提交 `e6cbc97e9faac83fed70afbb28069b6c83e8f216` 为产品代码基线；本地 `local-asr-prototype` 提供 ASR 服务、浏览器录音器、网关和既有测试。融合结果仅提交到 Gitee 的 `leo-fen` 分支，不修改 `master` 或 `dev`。`leo-fen` 当前只有文档骨架，因此需先以正常 Git 合并/变基方式引入 `dev`，不得强推覆盖远端历史。当前 ZIP 可用于离线开发；若 Git 凭据仍不可用，先交付本地可运行代码，远端推送单独标记为未完成。

## 方案选择

采用三进程边界：网页 Vite `127.0.0.1:5173`、会议看板 FastAPI `127.0.0.1:8000`、本地 ASR FastAPI `127.0.0.1:9000`。录音文件只发往本机 ASR；ASR 返回 `NormUtterance` 后，由网页提交给看板后端的单一归一化事件入口。后端复用 Store B、BoardAgent、Store A 和既有 `board.update` WebSocket 广播。手动发言继续使用现有 `/api/cli/push`，在编排、存储和图更新层与语音事件汇合。

最终仓库保留现有 `backend/` 与 `frontend/`，新增 `local_asr/` 放置原型的 FastAPI 服务与测试；原型网页不作为第二个产品入口移植，只复用其录音、接口和事件类型模块。服务间只通过 JSON 事件契约通信，不跨进程导入模型运行时。

比较过的替代方案：把模型加载到看板 FastAPI 进程可少开一个端口，但模型依赖、长时间初始化和故障会拖垮看板；保持两个独立网页则无法形成一体化产品。三进程方案保留已有模块边界和看板可用性，故为本阶段选择。

## 用户流程与界面

`dev` 的 X6 看板、看板娘、光标事件和手动输入保持现状。在同一页面的发言区加入录音开始/暂停/继续/停止、录音时长、ASR 服务与模型状态、最近一次转写和发送状态。停止录音后先显示“识别中”，成功时展示转写文本并自动发送事件到看板，收到成功确认后显示“已加入看板”；失败时保留转写文本及“重试发送”，不制造重复事件。麦克风不可用时显示音频文件上传入口；服务或模型不可用时手动文本框仍可提交。

首版是一段录制完成后识别，不提供逐字字幕、连续自动分句、多人声纹识别或会议平台 SDK。移动窄屏应能触达录音、状态和手动输入控件，不遮挡核心看板。

## 接口与数据契约

1. ASR 原有 `GET /health`、`GET /models/status`、`POST /v1/audio/transcriptions` 保持兼容。后端默认只绑定 loopback；模型缓存、音频临时文件和密钥不纳入 Git。
2. 前端通过 Vite 代理 `/asr/*` 到 `127.0.0.1:9000`，以同源路径查询状态和上传音频；生产静态部署时由部署配置提供等价代理，不在页面中硬编码跨域 URL。
3. 看板新增 `POST /api/utterances`，请求体为 ASR 返回的 `NormUtterance` JSON。入口校验必需字段、字段上限、时间范围、`is_final=true`、`is_partial=false`、非空文本；`meeting_id` 限制为安全标识符以避免文件路径穿越。将 `speaker` 映射到现有 dataclass，兼容可选 `source_id`、`translation`、`raw_ref`。拒绝不合法事件，不能静默改写为腾讯会议事件。
4. 以 `(meeting_id, utterance_id)` 去重，同一会议的提交串行化。首次接受时记录 Store B 元数据并驱动 BoardAgent；只有驱动成功才记录已处理标志，失败允许以同一 ID 重试。已处理事件重发返回成功且标明去重，不重复推理或创建节点。CLI 与腾讯会议入口逐步抽取共用的存储/驱动函数，保持旧 API 可用。
5. 服务器响应至少包含 `ok`、`utterance_id` 和去重标志；看板变更仍走现有 `board.update` 广播，网页断线后可用 `GET /api/board` 恢复。前端失败提示区分识别失败、模型未就绪、上传失败、看板提交失败。
6. 前端录音器沿用原型的 MediaRecorder 选择、轨道清理与大小/格式检查；录音和状态请求接受注入的 `meeting_id`，不保留写死的 `mtg_demo` 到可复用 API 函数里。

## 运行、隐私与降级

提供 macOS 本地启动说明/脚本：检查 Python、Node、ffmpeg 与端口；分别启动看板、ASR、Vite，并明确健康检查地址。启动看板不应等待 ASR 模型加载。ASR 首次下载模型可能需联网；模型未就绪时页面应继续可用。保留 `AMO_LLM_ENABLED` 配置：未提供密钥时明确为 MockLLM 演示，提供密钥后使用原有 OpenAI-compatible 客户端，不在本次集成中改写模型策略。

音频不由看板后端保存；ASR 临时解码文件按现有网关生命周期清理，默认不保存录音。网页不得把密钥注入前端。模型权重、`.env`、日志、运行数据与 `node_modules` 均保持忽略。

## 验收与验证

1. 看板后端原有测试和前端 TypeScript 构建通过；ASR 原型既有单元、接口和浏览器测试继续通过。
2. 新增契约/接口测试覆盖合法事件、字段错误、空文本、partial 事件、重复 `utterance_id`、Agent 失败、Store B 溯源和 WebSocket 看板更新。
3. 新增前端测试覆盖录音状态、上传和转写展示、自动提交、提交失败重试、ASR 不可用时手动发言保留。
4. 本地端到端烟测：手动文本使 X6 增加节点；使用测试 WAV 的 ASR 响应生成 `NormUtterance` 后，同一看板增加节点，Store B 可反查文本；重发同一事件不重复新增。
5. 在当前 Mac 上单独验证真实麦克风 → SenseVoiceSmall → 看板。若 FunASR 模型/依赖仍未安装或下载失败，报告具体阻碍，不以模拟音频或桩模型替代该项验收。
6. 远端提交前确认当前 `leo-fen` 与 `dev` 的 Git 关系、工作树差异和完整测试；只做非强制推送到 `leo-fen`。若无 Git 凭据，保留本地成果并清楚标记未推送。
